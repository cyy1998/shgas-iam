## 已确认的决定

### Q1：只自动完成离线数据迁移

维护者选择数据迁移完成作为脚本终点：调用者事先停流、停止并排空相关服务与任务；脚本负责数据库转换、
认证状态清理、Client Snapshot 清理和相应的独立核验。部署、启动服务和恢复流量仍由调用者处理。
“端到端”在本设计中限定为离线迁移流程，不等于自动发布系统；运行过程中无需人工确认、编辑中间文件或切换命令。

### Q2：自动选择唯一来源，歧义直接失败

维护者预期不会存在同时配置两个协议的 Client；一旦发现这种情况，脚本抛出异常，不猜测协议，
也不进入交互选择。正常路径不要求调用者手写 manifest，由脚本自动完成迁移编排。
无配置、停用和删除 Client 的处理及预检边界由 Q6 确认。

### Q3：目标只覆盖当前仓库版本

来源固定为 `b6481f2de5c2930fc381d99e70520e0783091e9d`。本次讨论时当前仓库最新提交为
`acc2bd7c558ce9b029bcb04d446a31ee6dbeca25`，本功能以该版本为目标基线。
不设计远端最新版本发现、自动拉取或未来任意目标版本的通用升级框架。

### Q4：失败保持停流，修复后重跑

维护者选择失败后停止、保持停流并保留恢复进度，修复原因后重跑同一入口。
不自动恢复旧数据库、旧部署或接入方配置，不因失败恢复业务流量。
已完成作用不能仅凭进程失败推断为回滚；恢复文件和重复执行语义由 Q7 确认。

### Q5：使用默认 namespace

维护者要求使用默认值，不要求人工新增迁移 namespace 配置。数据库和 Redis 连接沿用已有运行环境配置，
自动入口负责向各底层命令传递所需输入；旧、新认证状态清理采用对应版本的实际默认 namespace，
不从未知 key 推测其他部署范围。默认值的精确拼接须以旧、新 factory 和维护 adapter 的代码为准。
本决定不证明真实部署使用默认值，也不意味着连接到任意可达的本地数据库。

已核对的传入值：旧 Kernel 为 `sess:v2:`；当前 Kernel 和 Custom 均为 `iam:session`；
当前 OIDC 为 `iam:oidc`。旧 Custom redemption 与 Provider 的范围沿用 owner 的固定 key family，
不扩大为任意前缀删除。当前 owner 自行拼接各自的版本后缀，不把最终 Redis 前缀误作传入 namespace。
Worker Redis port/DB 的既有默认值为 `6379`/`0`，总入口须向要求显式参数的底层维护命令传入解析后的值。
数据库 URL 和 Redis host 没有代码默认值，仍须来自既有环境配置；`.env.example` 的示例连接不是部署默认值。

### Q6：全量 Client 检查与确定性转换

只有一种协议配置时自动选择该协议；没有协议配置时保留无协议。停用和删除的 Client 也参与检查和转换，
保留其原有状态。双协议或非法配置不跳过、不自行修复；所有可预先发现的此类问题在数据库迁移写入前统一报错。

### Q7：自动保存恢复文件，成功后的重跑不再执行破坏性步骤

脚本自动建立固定工作目录，保存 manifest、receipt 和执行报告，调用者无需编辑中间产物。
失败后用同一入口核对实际数据库与 Redis 状态再继续，不无条件重放九个数据库阶段，也不重新生成凭据身份。
完整成功后的再次运行只做核验，不再次生成 Secret，也不再次清理后来产生的登录态。
恢复文件缺失、跨资源误用或状态冲突时按 Q9 拒绝。

### Q8：备份与停流由调用者提前完成

备份、关闭流量以及停止并排空相关 reader/writer 均为调用者已完成的前置条件。
脚本不调用备份系统、不自动恢复备份；执行失败非零退出，保留恢复文件，等待修复后重跑。

### Q9：只接受原始来源或本脚本的可验证恢复

首版只支持原始 b648 首次执行，以及本脚本自己中断后的续跑。
数据库已发生迁移但必要恢复文件缺失、资源不匹配或数据状态冲突时，直接报错。
不自动重建丢失的保留证据，不接管原手动命令已迁移一半但缺少本脚本完整恢复记录的环境。
工作目录中的阶段记录不能单独证明数据库或 Redis 阶段完成，续跑仍须核对实际状态。

### Q10：首次成功与成功后重跑分别验收

首次成功必须完成数据库最终核验、source 与目标认证状态独立清零核验、Client Snapshot 独立清零核验，
并证明非目标数据保留。任一异常都不能报告成功；删除计数或子命令启动成功不能代替独立核验。
已经成功后的再次运行允许存在新登录态，只做适用的只读检查，不再要求认证状态清零，也不再次清理认证或 Snapshot 状态。
真实部署和业务登录验证仍由外部发布步骤负责。

使用真实 PostgreSQL/Redis 覆盖以下行为：

- 从固定 b648 来源通过单入口一次完成全部离线迁移。
- 双协议在数据库迁移写入前拒绝；全量 Client 的合法状态按 Q6 保留。
- 关键阶段中断后使用原恢复记录续跑，核对部分已提交作用，不重复轮换 Secret。
- 必要恢复记录缺失、冲突或资源不匹配时拒绝，不绕过保留事实核验。
- 首次迁移的目标认证状态和 Snapshot 清零，非目标业务数据与 Redis 状态保留。
- 完整成功后再次运行不写入、不再次清理，并保留后来产生的新登录态。

## 实施与验收

`pnpm --filter @iam/worker b648-upgrade` 由脚本目录内的 `run.ts` 组合原数据库分阶段 CLI、在线状态 owner CLI
和 Snapshot CLI。恢复文件由 `recovery.ts` 保存；`preservation.ts` 对非目标 PG/Redis 事实作独立比较，
Redis 范围通过各 owner 的只读 verifier 取得，不复制清理 pattern。成功状态原子写入必需的 `state.json`，
因此成功后丢失可选报告不能触发再次清理；必需 state 丢失而数据库已推进则拒绝。

Worker composition 测试使用精确旧 migrations 和真实 PG/Redis，已验证首次全链、双协议预检拒绝、
apply/contract/finalize 失败恢复、Redis 部分失败、凭据稳定、恢复记录冲突、未知记录保留、
非目标 TTL 漂移阻断以及完成后重跑保留新登录态。
