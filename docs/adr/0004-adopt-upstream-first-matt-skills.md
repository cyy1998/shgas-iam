# 采用上游工作流与仓库薄适配

仓库以 `mattpocock/skills` 拥有澄清、spec、tickets、实现和评审等通用方法，GitHub Issues 保存跨会话需求与协作状态。
本页合并原 OpenSpec 退役与上游优先决定，并纳入已经接受的 GitHub tracker 和 Sandcastle AFK 调整。

## 理由与代价

同时维护上游 skills、累计 capability specs 和本地证据状态机会造成多套事实来源与重复元数据。仓库只记录上游无法知道的
领域、分支、验证、授权和收尾约束，不复制通用流程，不再以专用 checker 强制 tracker 内部结构。

当前行为以实现、生效配置和可执行证据为准；spec/ticket 表达修改目标，不证明已经交付。领域语言和已接受决策约束设计，
但不能覆盖已观察到的实现差异。目标冲突仍须澄清。

`openspec/` 与退役的 `.scratch/` 保持原路径、只读追溯；不批量转换、补证或重新解释历史。仍有价值的历史内容只在相关
区域被触及时，经核验提升到当前文档。新工作不继续写这两套 tracker。

代价是放弃累计 capability-spec 视图与机器证明的交付状态链，依赖清晰的 issue、普通 Git 提交、执行者和独立评审。
聚焦验证服务日常反馈，最终验证与收尾按仓库工作流执行；采用上游不取消本地授权边界。

## 当前契约与历史

2026-09-21 采用作者自用 Sandcastle 运行模型，使无人值守工作独立于持续在线聊天主会话。
2026-09-22 引入仓库预定义实施者档位和独立 Standards/Spec 评审角色，固定职责、模型与思考程度，
使执行策略可以审查和追踪；容器内角色配置由 runner 提供。原批次普通交付、逐票最多十轮评审的取舍已由下节修订替代。

2026-10-10 手动完整 Spec 改为直接采用 `implement-spec`，项目文档只保留仓库差异，评审和全仓验证集中到集成候选。
2026-10-14 取消仓库追加的修复后循环全量复审：累计重读会重复消耗上下文，修复由受影响检查验证，
代价是不默认获得修复后的独立复审。AFK 的现行节奏统一见下节。

取消强制独立设计提交和已有实施授权下的阶段重复确认，保留最终本地 squash 合入的单次人工授权。
小任务直接实施和验证，`implement` 及其双轴评审仅在用户显式调用时适用。这减少小改动的编排成本，
也意味着小任务不默认获得独立双轴审查，维护者可单独要求 `code-review`。

### 2026-10-25：AFK 按 Spec 动态实施与集中验收

AFK 继续从全仓可执行 backlog 自动选取工作，以 Spec 为交付单位：完成一个 Spec 后继续下一个，
同一 Spec 内按依赖图动态并行，ticket 完成后及时合入并解锁后续工作。逐票执行聚焦验证，
正式双轴评审、集中修复与最终验证移到整个 Spec 的集成候选，与手动 `implement-spec` 的节奏对齐。
运行预算改为 Spec 数量，默认最多尝试 1 个 Spec、最多并行实施 4 张 ticket，两者均可配置。
恢复旧 Spec 也计入本次额度；已开始的 Spec 推进到完成或无法继续后，再在剩余额度内选择下一个。
沿用现有超时与中断清理机制，本次不增加费用或 token 预算系统。

宿主 runner 继续负责调度、并发、完成事件、执行器生命周期和恢复，agent 负责理解依赖、实施、合并与评审。
每个 Spec 使用独立集成分支，优先核对并复用已有匹配功能分支；ticket 完成后普通 merge 到集成分支，
整个 Spec 通过评审和最终验证后再 squash 到调用分支。这保留 AFK 对持续在线主会话的独立性，
代价是仍需维护 runner 调度代码；未完成 Spec 的工作保留在集成分支中。

本次设计仅覆盖有父 Spec 的 implementation tickets，不考虑独立 ticket。选中 Spec 后读取完整依赖图，
父 Spec 和每张待实施 ticket 均须具备 `ready-for-agent`，子票还须满足认领条件；选择父 Spec 本身不扩大子票实施授权。
未获授权或被他人认领的必要切片作为阻塞记录。

新增互斥类型标签 `type:spec` 与 `type:ticket`，分别识别需求与实施切片，triage 标签继续表达是否允许实施。
AFK 按类型标签识别，缺失或冲突时不自动实施；创建 Spec 和拆票流程负责写入正确类型。
ticket 必须通过 GitHub 原生父子关系关联到一个带 `type:spec` 的父 issue，程序据此收集完整子票，
正文链接只辅助阅读。关系缺失或矛盾时报告修正，不从标题或正文猜测归属。
这使程序识别与模型理解需求分离，代价是手动创建和拆票也必须维护类型与原生关系。

Spec 内依赖按前置票已验收并合入当前集成分支解锁，此时 ticket 仍保持 open；整个 Spec 完成评审、
最终验证并 squash 到调用分支后，再关闭 tickets 与父 Spec。跨 Spec 依赖必须等前置成果交付到调用分支。
依赖可执行与 issue 已交付由此分开，避免将未交付的中间成果标为完成。

前置依赖采用 GitHub 原生 blocking 关系，由程序计算可执行切片；正文解释原因，模型发现遗漏时报告，
不静默改写依赖图。关系矛盾、循环依赖或未登记的必要依赖暂停受影响切片，其他独立切片继续。
本次设计以运行期间需求、父子和阻塞关系及准入标签保持稳定为前提，不实现运行中变更检测与重新规划。

单票失败时继续完成当前 Spec 中不依赖它的在途工作和可执行切片；没有可推进工作后保留恢复点，
剩余额度允许时再选择其他可执行 Spec，本次运行不反复挑回同一个失败项。Git 状态异常、执行器无法停止或公共基础设施故障
则停止整次运行。

实施者可以在自己的会话内正常修复和验证；最终双轴评审后由一个实施者集中修复，不默认循环复审。
会话失败或结束时仍有未解决问题则保存进度，本次运行不为该失败任务反复新开会话，下次启动再恢复。

后续启动优先恢复符合准入条件的未完成 Spec，再选择新 Spec。沿用 Git、issue 普通交接及已有日志核对进度，
不新增实施进度 checkpoint 或专用恢复记录：
已验收并合入集成分支的 ticket 复用，未完成票从保留分支继续，已 squash 但关票中断的 Spec 只补收尾。
调用分支前进时先整合新基线并重跑失效检查，影响评审依据时重新评审；分支归属或交付状态无法确认时
保留现场并报告，不自动重置。

改造通过自动化行为测试、临时真实 Git 仓库与既有 Docker smoke 验收：覆盖动态调度、依赖解锁、并发、
失败后的独立工作、合并与 squash、中断恢复和避免重复交付；GitHub 使用受控响应验证类型、关系和关票时机。
Docker smoke 覆盖新角色、prompt 与资源清理接线。这些检查不证明真实模型的实施质量，
首次真实 Spec 执行作为后续实际运行验证，不在测试中自动操作现有 backlog。

启动 AFK 仍授权本次运行在调用分支本地合入，以及更新和关闭已验收 tickets 与完成的父 Spec；
push、PR 和部署继续单独授权。

这个决定取代继续保留 AFK 批次屏障、逐票循环评审和逐票全仓静态检查的方向，减少无依赖票之间的等待与重复检查。
代价是跨票问题集中到 Spec 集成阶段发现，失败时需要保留整个 Spec 的可恢复工作。
运行与恢复规则见[AFK 工作流](../agents/sandcastle-afk.md)，可执行入口和 smoke 的证明范围见
[AFK 命令](../development/commands.md#sandcastle-afk)。本地实现与自动化验收不代表已合入主分支或已部署。

操作规则见[开发工作流](../agents/workflow.md)、[议题跟踪](../agents/issue-tracker.md)及
[事实与目标](../index.md#当前事实与修改目标)。
