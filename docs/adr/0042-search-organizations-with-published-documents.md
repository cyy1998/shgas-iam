# 使用异步发布的组织文档执行筛选并返回结果

Organization Search 保留组织关系表作为唯一源事实，以 PostgreSQL JSONB 保存可重建的搜索文档。
文档由后台任务异步构建，承载组织自身属性和完整路径；新 Internal DSL 返回用于匹配的同一份完整文档。
这是当前实现采用的已接受决定，完整契约见 [Organization Filter DSL](../features/organization-search/filter-dsl.md)，维护流程见[组织搜索维护](../releases/organization-search-maintenance.md)。
实施与验收由 [Spec #221](https://github.com/cyy1998/shgas-iam/issues/221) 跟踪，不以本决定推定实现或部署已完成。

## 理由与取舍

组织关系、生命周期命令与既有调用方继续依赖源事实；搜索文档服务于读取，不成为第二个业务写入口。
将完整路径事实放入派生文档，旨在减少每次查询反复组装层级的工作。本次明确不做性能验收，
不要求基准数据、执行计划、延迟采样或压测；采用 JSONB 的设计意图不作为已经测得性能提升的结论。

采用异步构建，接受业务写入成功后查询仍可能使用旧事实，避免把后代文档的完整重建纳入每次祖先资料修改的源事务。
相应代价是必须持久保存待重建工作，并承担发布、失败恢复及祖先变更传播的职责。
发布以单个组织为边界，单份文档内部一致，但接受不同组织的新旧版本并存、新建暂不可见及删除延迟退出搜索，
不承诺固定更新时间；合法旧文档在构建失败时继续可读。这避免把一次祖先修改变成整棵子树的原子发布流程。

祖先资料变化采用源事务内持久登记、提交后展开子树、再按组织重建的传播方式。
只在源事务中扫描子树会漏掉并发新建后代，文档版本仲裁也无法补回未登记的变化；可靠展开阶段消除这一缺口，
代价是增加一类需要恢复的持久处理记录。队列只负责唤醒，不成为待处理事实的唯一来源。

固定返回匹配文档，既保留路径及层级供调用方解释结果，也避免从当前源表或另一份摘要拼装出与筛选事实不同的响应。
代价是完整路径增加存储和响应体积，因此保留有界过滤与 500 条结果上限。
这与 [ADR-0015](0015-adopt-schema-driven-user-profile-filter-dsl.md) 的 User Profile Base 响应属于不同结果根的决定，
不改变用户 DSL 的摘要与一致性边界。

## 范围

首版只搜索组织自身属性与完整路径，不收录成员、岗位、角色或责任持有人条件。
只新增组织 DSL；既有组织搜索与详情保留原契约和读取方式，不在本决定中迁移或弃用。

组织读模型独立管理文档版本、待处理记录和数据核验，首次完整构建并核验后开放新接口，
不与 User Profile 绑定发布或恢复。组织文档直接从 PostgreSQL 查询，首版不增加 Redis 文档缓存。

文档采用独立单代 schema；首次构建或不兼容升级在组织搜索维护窗口内重建并完整核验，不提供调用方版本选择、
跨 schema 混读或回退。恢复沿用维护命令与外部周期调度模式，不新增仓库调度系统，不在搜索请求中修复数据。
