# Sandcastle AFK 工作流

本页只在运行或维护 Sandcastle AFK 时读取，保持无人值守实施的独立授权、分支和 Spec 最终评审约定。
维护者运行 `pnpm sandcastle` 或明确要求启动该路径，即授权本次运行处理全仓 `ready-for-agent` backlog、
在调用分支本地合入、评论及关闭已验收 tickets 和完成的父 Spec；配置执行器本身不等于启动它。

## 分支与工作区

AFK 在启动时固定调用分支，每个 Spec 使用独立集成分支与 worktree；每张 ticket 在自己的分支与 worktree 中，
从当前 Spec 集成内容开始实施，交接前整合最新集成内容，并以普通 `git merge` 进入 Spec 集成分支。
整个 Spec 最终验收通过后，以一个 squash commit 进入调用分支。已有分支先核对归属与恢复交接，不能覆盖未完成工作。运行期间调用分支由该 runner 独占写入；启动 AFK 的授权已包含这些本地合入，不包含 push、
PR 或部署。

## 双轴评审子代理生命周期

正式双轴评审在整个 Spec 的全部必要 tickets 已验收且普通合入集成分支后执行。部分集成、空子票列表、
issue 的 closed 状态或单票成功声明均不能代替完整集成证据。宿主核对每票交接和 Git 祖先关系，固定本次
review base 与集成 candidate SHA；评审期间工作区和候选保持不变。

最终评审协调会话按 `.agents/skills/code-review/SKILL.md` 新建相互独立的只读 Standards 与 Spec 子代理，
向两轴提供同一完整 diff、提交列表和固定 SHA。Standards 按仓库规范审查；Spec 对照完整父 Spec、全部必要
tickets、评论与已确认验收。两轴都实际结束并取得真实报告才完成评审收集，任一报告缺失、失败或候选不符均保持未完成。

后续由一个实施者会话阅读两轴报告，集中处理全部 findings、提交修复并执行最终验证，沿用手动 `implement-spec`
节奏，不默认循环双轴全量复审。集中修复使用既有实施者档位：涉及 deep 票沿用 deep，其余使用 standard；模型与思考
档位仍由角色文件定义。评审协调者使用调用者配置的模型，两个只读子代理使用各自角色配置。

角色以单层调用执行：评审协调者启动两轴子代理，集中修复者作为后续独立根会话运行，不增加嵌套调用层级。
宿主不解析自然语言 findings 或会话事件判断通过；评审协调者保留真实两轴报告，修复者逐项说明处置、实际命令结果
与未执行项，只有 findings 妥善处理且必需检查全部通过才输出其完成标记。会话失败或工作未完成时本轮不重开重试。

最终普通 issue 交接保留 review base、评审 candidate、修复后最终 candidate、两轴报告及修复验证材料，明确两候选
关系。最终门禁通过只表示可以交付，tickets 与父 Spec 在实际 squash 交付前保持 open；交付阶段核对真实 Git 与交接。
恢复依赖 Git、普通 issue 记录和已有日志，不新增实施进度 checkpoint 或专用 tracker schema。

## 批量实施

批量路径参考作者自用的
[Sandcastle runner](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/.sandcastle/run.ts)，
由本机 runner 调用 Docker 中的 Codex CLI，无需聊天主会话持续协调。Spec 选择、动态集成和集中最终验收采用本仓库适配，
实施和评审方法复用既有 skills。三个阶段如下：

1. **Planner**：宿主分页读取全仓 open `type:spec` 候选、完整原生子票及 blocking 关系，校验父子类型、准入和认领，
   将可信任务图、可执行切片与阻塞原因传给 Planner。父 Spec 与待实施子票均需 `ready-for-agent`；
   父子关系决定归属，原生依赖决定先后，正文只提供需求和解释。缺失/冲突类型、关系矛盾、循环依赖或未满足的
   前置条件阻止受影响切片，独立切片仍可选择；全部受阻时不尝试受阻票。assignee 用于保护他人工作，
   经过普通 Git/issue 交接确认的本 runner 工作可恢复。Planner 每次只选择一个 Spec 的可执行子票，
   宿主再次校验计划；父 Spec 不进入实施列表，空子票也不构成已完成的依据。
   Planner 为每票从仓库定义的 `implementer_light`、`implementer_standard`、
   `implementer_deep` 中选择实施者并说明理由：范围明确的小修改可选 light，常规功能或信息不足选 standard，
   涉及安全边界、并发、一致性或复杂重构选 deep。Runner 校验角色名称并加载对应配置。
2. **Implementer**：每票在独立分支、worktree 和全新会话中读取 `AGENTS.md`、ticket、父 Spec 与相关评论，
   认领后按 skills 实施、运行完整受影响范围的聚焦验证并创建正常提交。交接保留独立基线、候选、真实命令与结果、
   未执行项和剩余问题；不逐票运行正式双轴评审或固定全仓静态检查。票级验收会话整合最新集成内容、验证后交给串行合入流程。
   必需检查失败或未执行时保持未完成，保留分支和工作树。
3. **Spec 集成与最终验收**：宿主串行将已验收候选普通 merge 到 Spec 集成分支；Spec 内依赖以票已验收并集成为
   解锁依据，ticket 仍 open。单票失败后继续独立切片；所有必要票集成后，按上一节执行一次集中双轴评审、单实施者修复与
   最终验证。通过门禁的最终候选才交给交付阶段，以一个 squash commit 本地合入启动分支；核对交付事实后统一记录并关闭
   tickets，再关闭父 Spec。未通过门禁时保留实际进度，不能用部分成果冒充完整 Spec；默认不循环全量复审或重开失败会话。

GitHub Issues 保存需求、协作状态与恢复说明，Git 提交保存实现历史；日志和本地分支辅助恢复，不替代 issue 事实。
未完成成果保留在 Spec 集成分支；本轮不反复挑回失败项。无法自行解决时报告阻碍和恢复点。
保留分支和工作区现场，不自动 reset 或重复合入。
未完成或缺少必需检查的 ticket 保持 open；正常进程退出、存在提交或 Implementer 宣称完成都不能替代验收结果。
票级验收在整合最新内容或提交修复后失败时，普通交接记录实际 HEAD、准确分支和路径及待完成验证；
下次启动核对这些事实后重新验收，不能沿用旧候选或把失败当作已集成。

## Spec 交付与清理

最终验收交接只授予交付资格。宿主再次核对调用分支、启动基线、评审候选、修复后候选与各票普通合入的祖先关系，
调用与集成工作树必须干净且创建者已确认停止。调用分支前进、候选变化或交接缺失时保留现场，先整合新基线并更新失效的验证；
影响评审依据时重新评审，不能强行使用旧门禁。

交付以 `git merge --squash` 和一个聚合提交完成，提交保留父 Spec、调用与集成分支、review base、评审与最终候选。
宿主确认调用分支只新增该提交、单一 parent 为验收基线、文件树与最终候选一致、工作区干净后，才写普通 issue 交接，
关联真实 squash SHA、两轴报告及修复验证摘要；逐一记录、关闭并核验 tickets，最后记录、关闭并核验父 Spec。
调用分支交付不包含 push、PR 或部署；CLI 只有实际交付与关票完成才报告该 Spec 成功。

提交、记录或关票失败均停止后续收尾，保留已产生的提交、暂存内容、分支和工作树，交接说明实际 HEAD、已确认关闭项及
下一安全动作。squash 成功但记录或关票中断时，恢复先核对普通 Git 与 issue 事实，只补剩余收尾，不重复 squash 或 reset。
未知 Git 状态与 GitHub 公共故障会停止整个 runner。恢复识别属于后续启动流程，不能把失败进程的正常退出当作交付证明。

全部关票后才回收本 Spec 不再需要的票级和集成工作树及本地分支。清理前统一核对候选、干净状态、准确 worktree 登记和锁，
并确认所有创建者停止；任一项不明就保留。移除使用准确路径且不强制，删除 ref 时匹配已观察候选，不强删偏移分支或未知工作。
清理失败保留实际阶段，代码交付与环境回收分别核对。
跨 Spec 前置交付通过持久 squash 提交、单一 parent、普通 trailers 与交付评论的匹配及启动分支祖先关系核验，
允许采用其他协作者的真实交付记录，不依赖清理后可能已被回收的实施提交对象。closed 状态本身不构成交付证明。
未完成工作的恢复仍按当前 runner 作者、认领和严格 Git 对象核验保护归属，不因读取他人的交付事实而接管其工作树。

运行环境、命令和当前资源限制见 [Sandcastle AFK 命令](../development/commands.md#sandcastle-afk)。

## 验证节奏

通用的聚焦验证、提交 Hook、修复后的结果复用和基线失败处理按[工作流补充](workflow.md#验证节奏)执行。

- 票级实施与验收运行完整受影响范围的行为测试、typecheck 和适用文档检查，以及 `git diff --check`。
- 最终集中修复者在整个 Spec 的最终集成内容上执行一次 `pnpm verify`，并按父 Spec 与全部 tickets 的风险、验收和
  已确认测试决策补齐所需 Integration、E2E、Gateway 等检查；重复覆盖按范围去重。各票分支结果不替代最终组合验证。
- 后续修复重跑失效检查，仍有效的通过证据可复用。普通交接记录实际命令、结果、对应候选与未执行项；必需检查失败或
  未执行、findings 尚未解决时保持未完成。本轮不通过反复新开会话重试，也不以清理成功或进程正常退出代替验收。

专用测试资源遵守[资源隔离](../architecture/testing-architecture.md#专用资源与隔离)；
AFK sandbox 通过共享宿主 daemon 和 host networking 调用正式根测试入口；每条命令使用动态 loopback 端口和独立 project。
执行器只管理 Docker 接入、稳定运行记录与异常恢复，不预建或跨命令复用 PostgreSQL/Redis。
外层先停止并等待准确的创建者 sandbox，再按本执行器 registry 复用公共清理入口，尊重显式 keep，最后关闭 worktree 与配置。
无法确认创建者已停止时保留挂载和恢复记录，不先清理仍可能创建资源的执行器环境。恢复命令见[命令页](../development/commands.md#sandcastle-afk)。
Linux 依赖通过每执行器匿名磁盘卷隔离，实际 workspace 的安装覆盖和版本检查见命令页。
卷 ID 只记资源归属，在模型命令前保存；确认创建者停止后按准确容器和 ID 回收，不作为实施进度来源。
私有 registry 的认证由调用者显式提供受支持的配置；执行器只读挂载私有副本，不自动继承宿主凭据。
副本同样等创建者停止后回收；停止未确认时与其他恢复材料一起保留，使用同一准确执行器恢复入口。
配置格式、源文件责任和回收边界统一见[AFK 命令](../development/commands.md#sandcastle-afk)。
